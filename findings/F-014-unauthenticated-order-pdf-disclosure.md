# Finding F-014: Missing Authentication Exposes Other Customers' Order Confirmation PDFs via Public Directory Listing

| Field | Value |
|---|---|
| Finding ID | F-014 |
| Title | Unauthenticated Retrieval of Order Confirmation PDFs, Directly Enumerable via Directory Listing on `/ftp/` |
| Category | OWASP Top 10 — A01:2021 Broken Access Control (also A05:2021 Security Misconfiguration, for the directory-listing delivery mechanism) |
| Severity | **High** |
| Status | Confirmed |
| Affected Component | `GET /ftp/order_<orderConfirmation>.pdf`, exposed via directory listing at `GET /ftp/` |
| Date Identified | 2026-09-29 |

## Summary

Every completed checkout generates a PDF receipt named `order_<orderConfirmation>.pdf`,
saved into the same public, unauthenticated `/ftp/` directory already flagged during
recon (`attack-surface-map.md`, Section 5) as having directory listing enabled. This
finding confirms two things beyond that original recon note: first, that the exposed
directory listing includes other customers' order receipt filenames in plain view —
no guessing or enumeration required, the exact filenames are handed to any visitor who
simply browses `/ftp/`; and second, that the PDF itself is retrievable with **zero
authentication** — no session cookie, no `Authorization` header, no ownership check of
any kind.

Unlike a typical IDOR that requires guessing a sequential numeric ID (as in F-005), an
attacker here does not need to guess anything at all — the directory listing is a
built-in "menu" of every retrievable order document currently on disk. This makes the
finding more directly and trivially exploitable than a pure ID-enumeration bug, even
though the order confirmation string itself does carry meaningful entropy (see
Follow-Up Testing).

## Steps to Reproduce

1. With no active session, no cookies, and no `Authorization` header, browse the
   exposed directory listing:
   ```
   GET /ftp/ HTTP/1.1
   Host: localhost:3000
   Accept: text/html
   Connection: keep-alive
   ```
2. Observe the response lists, among other files, order confirmation PDFs belonging to
   other accounts, named `order_<orderConfirmation-id>.pdf` — the exact filename
   needed for direct retrieval, with no guessing involved.
3. Request one of the listed order PDFs directly, again with no authentication
   whatsoever:
   ```
   GET /ftp/order_1aed-18b1f1f329bf8830.pdf HTTP/1.1
   Host: localhost:3000
   Accept: */*
   Connection: keep-alive
   ```
4. Observe `200 OK` with the real, complete PDF file returned in the response body —
   no session, no ownership verification, no rejection of any kind.

## Evidence

**Directory listing (`GET /ftp/`, no authentication), excerpt showing exposed order
PDFs alongside other previously-known sensitive files:**
```
<a href="order_1aed-18b1f1f329bf8830.pdf">order_1aed-18b1f1f329bf8830.pdf</a> (1753 bytes, 9/29/2026 10:08:01 PM)
<a href="order_57f7-1c0b9e56477137e4.pdf">order_57f7-1c0b9e56477137e4.pdf</a> (1855 bytes, 9/29/2026 11:18:01 PM)
```
Both filenames — and therefore both order confirmation IDs — were fully disclosed by
the directory listing itself, with no prior knowledge of either order required.

**Direct retrieval, no `Authorization` header, no `Cookie` header:**
```
GET /ftp/order_1aed-18b1f1f329bf8830.pdf HTTP/1.1
Host: localhost:3000
Accept: */*
Connection: keep-alive

HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Length: 1753
Last-Modified: Tue, 29 Sep 2026 22:08:01 GMT

%PDF-1.3
...
/Producer 11 0 R   (11 0 obj: "PDFKit")
/Creator 12 0 R    (12 0 obj: "PDFKit")
/CreationDate 13 0 R  (13 0 obj: "D:20260929220801Z")
...
```
The returned content is a genuine, well-formed PDF (valid `%PDF-1.3` header, xref
table, and trailer), generated by the `PDFKit` library at the exact timestamp matching
the checkout that produced order `1aed-18b1f1f329bf8830` earlier in this assessment
(see `F-005` evidence, Sub-Finding section) — confirming this is a real order receipt,
not a placeholder or unrelated file.

The second listed file (`order_57f7-1c0b9e56477137e4.pdf`) was confirmed present and
its size/timestamp metadata exposed via the same unauthenticated directory listing
request; its content was not independently re-fetched in this session, since the
identical retrieval mechanism was already proven successful against the first file.

Full raw requests/responses saved in
`evidence/requests-responses/F-014-unauthenticated-order-pdf.txt`.

*(Sanitization note: the PDF's raw compressed stream content should be retained as-is
for evidence purposes — it contains only synthetic test-account order data, no real
customer information.)*

## Impact

- **Any anonymous visitor can retrieve any customer's order confirmation document**
  without authenticating at all, as long as the order confirmation ID is known —
  and the directory listing itself supplies that ID directly, removing even the need
  to guess or enumerate it.
- **Directory listing converts what would otherwise be a moderate-effort ID-guessing
  problem into a zero-effort disclosure.** An attacker does not need to know anything
  about the target in advance — simply browsing `/ftp/` reveals every currently-stored
  order PDF's exact filename.
- In a real production deployment, **every completed order** would generate and store
  a PDF in this same public, listable, unauthenticated location — meaning the full
  history of every customer transaction on the platform would be continuously exposed
  to any anonymous internet visitor for as long as the receipt files remain on disk.
- Order confirmation PDFs of this type typically contain the customer's name, ordered
  products, quantities, prices, and delivery details — the same class of information
  F-001 and F-007 already established this application treats as sensitive elsewhere.
  This finding shows that sensitivity is not consistently protected across every place
  such data is generated and stored.
- This compounds the existing recon-stage observation (`attack-surface-map.md`,
  Section 5) that `/ftp/` directory listing exposes internal business documents
  (`acquisitions.md`) — this finding proves the same misconfiguration also exposes
  **customer-facing transactional data**, a materially more serious category of
  information than internal file listings alone.
- Rated **High** rather than Critical because retrieval is scoped to individual order
  documents rather than a full database dump or account takeover, and because this
  local instance only contains synthetic test-account orders — but the complete
  absence of any authentication or ownership check, combined with trivial,
  guess-free discoverability via directory listing, places this well above a
  purely informational or Low-severity misconfiguration.

## Root Cause

Two independent gaps compound each other here:
1. **Directory listing is enabled on `/ftp/`** (already noted in recon), which
   exposes the filesystem contents of a directory that includes dynamically
   generated, customer-specific files alongside static/seed content — the
   application does not distinguish between "safe to list" and "sensitive, must not
   be listed" content within the same directory.
2. **The file-serving route for `/ftp/*` performs no authentication or ownership
   check at all** (only an extension whitelist, per the `.bak` file-type testing
   conducted in this same assessment) — it treats every file in the directory as
   equally public once its exact name is known, regardless of whether that file was
   meant to be broadly accessible (e.g., a public FAQ) or privately scoped to one
   customer (e.g., an order receipt).

## Remediation

1. **Never write customer-specific, sensitive documents (order receipts, invoices,
   etc.) into a publicly served, listable directory.** Store generated order PDFs in
   a private storage location not reachable by any public route.
2. **Serve order confirmation documents only through an authenticated,
   ownership-checked endpoint** — e.g., `GET /rest/orders/:id/receipt`, which verifies
   the requesting user's session matches the order's owning account (or that the
   requester holds an `admin` role) before returning the file, following the same
   ownership-verification pattern already recommended for F-005 and F-012.
3. **Disable directory listing entirely** on `/ftp/` and any other publicly reachable
   static-file route, regardless of what content is believed to currently reside
   there — directory listing should never be relied upon as a soft protection for
   files that are individually reachable by direct URL.
4. **Apply the same extension-whitelist-plus-authentication combination consistently**
   — the extension whitelist tested in this assessment (`.md`/`.pdf` only) is a
   reasonable content-type control, but it is not a substitute for an authorization
   check and should never be treated as one.

- **F-001 / F-007** (Sensitive Data Exposure via JWT / Full Database Extraction) —

  consistently protected to the same standard.

## Follow-Up Testing (planned)

- [ ] Independently re-fetch `order_57f7-1c0b9e56477137e4.pdf` directly (not just via
      listing metadata) to complete full confirmation of the second sample.
- [ ] Generate several more real orders in quick succession and compare the full set
      of confirmation IDs to determine whether the ID format (prefix + suffix) carries
      predictable structure — current sample size (3 full IDs observed) was
      inconclusive: two orders shared an identical 4-character prefix (`1aed-`) while
      a third used a different one (`57f7-`), with no clear sequential pattern in the
      suffixes. This matters only as a secondary attack path (ID guessing without
      directory listing); it does not affect this finding's core conclusion, since
      directory listing already discloses exact filenames without any need to guess.
- [ ] Confirm whether disabling directory listing alone (without adding
      authentication) would be sufficient in practice, or whether direct requests to
      a correctly-guessed/known filename would still succeed — current evidence
      already answers this: yes, direct requests succeed regardless of the listing,
      confirming authentication is the necessary fix, not just hiding the listing.
